## 一、容器运行时（containerd 2.x 的"新世界"）

### 1.1 containerd 2.2 配置结构大变（最隐蔽的坑）

**现象**：按网上 1.x 教程改 `sandbox_image` 无效果；改完 grep 配置找不到该键。
**排查**：`containerd config default` 生成的是 `version = 3` 格式，键结构完全不同。
**根因**：containerd 2.x 把沙箱镜像从 `sandbox_image`（CRI 段）改名为 `sandbox`，挪到 `pinned_images` 段；默认镜像也从 `pause:3.9` 变成 `pause:3.10.1`（registry.k8s.io）。
**解决**：`sed "s#sandbox = 'registry.k8s.io/pause:3.10.1'#sandbox = 'registry.aliyuncs.com/google_containers/pause:3.10'#"`。
**经验**：**先 `containerd --version` 看大版本再查对应文档**。2.x 与 1.x 的运维命令、配置格式差异巨大，老教程全失效。

### 1.2 containerd 2.2 的 hosts.toml 不生效（两次踩坑）

**现象①**：Harbor 自签证书——hosts.toml 配了 `[host] ca = ...`，拉镜像仍报 `x509: unknown authority`。
**现象②**：docker.io 加速——hosts.toml 配了 daocloud/1ms mirror，拉镜像仍直连官方被代理重置。
**排查**：containerd 日志显示 `host="harbor.k8s.local:30443"`（解析到了），但 TLS 校验仍用系统 CA。
**根因**：containerd 2.2 对 hosts.toml 的 `ca`/mirror 配置处理有变化（或对多路径 config_path 支持问题），实测未按预期生效。
**解决**：放弃 hosts.toml，**把 CA 加入系统信任库**（`update-ca-certificates`）+ containerd 重启——一劳永逸。docker.io 镜像则**全部私有化到 Harbor**。
**经验**：containerd 2.x 环境，**"系统信任库 + 镜像私有化"是比 hosts.toml 更可靠的路径**。别再浪费时间调 hosts.toml。

### 1.3 /etc/containerd 目录不存在

**现象**：`containerd config default > /etc/containerd/config.toml` 报 No such file。
**根因**：containerd 随 Docker 安装，从未生成配置目录。
**解决**：`mkdir -p /etc/containerd`。
**经验**：新环境先确认目录存在；Ansible playbook 里必须带 mkdir（我当时也漏了，worker 上又踩一次）。

### 1.4 containerd 2.x 按 digest 匹配镜像（"假成功"陷阱）

**现象**：从 Harbor 拉 nginx:v1 秒成功，但 containerd 日志**没有 PullImage 记录**。
**根因**：之前冒烟测试拉过 nginx:latest，与推送的 nginx:v1 是同一内容（同 digest），containerd 2.x 按内容寻址直接命中本地，**根本没访问 Harbor**。
**解决**：用集群从未见过的 alpine 重新验证，日志确认真实 PullImage。
**经验**：**验证"从私有仓库拉取"必须用全新镜像**，否则 digest 命中会给你假阳性。

## 二、网络与镜像源（国内环境特供）

### 2.1 DHCP IP 漂移导致整个集群报废

**现象**：重启后 etcd/apiserver 崩溃循环，kubelet 疯狂报错。
**排查**：kubelet 日志显示连 `192.168.80.33:6443`，但机器真实 IP 是 `.133`——**kubeadm init 时 DHCP 给的 IP 与当前不一致**，证书、kubelet.conf 全绑死在旧 IP。
**根因**：DHCP 重启重新分配地址。
**解决**：`kubeadm reset` + 静态 IP + 重新 init。教训深刻。
**经验**：**建集群前必须先固定静态 IP**（含禁用 cloud-init 接管网络），这是第一优先级的坑。

### 2.2 镜像源逐个被墙（docker.io / ghcr.io / quay.io / registry.k8s.io）

**现象汇总**：
- docker.io：`auth.docker.io` 连接被代理重置（fake-ip 198.18.x.x）
- ghcr.io：flannel 新版本镜像 CDN（pkg-containers.githubusercontent.com）TLS 超时
- quay.io：prometheus-operator 镜像 ContainerCreating 卡死 10 分钟
- registry.k8s.io：间歇性可达（kube-state-metrics 曾 16 秒拉成功）
**排查**：逐源 curl 测连通性；发现**能通的部分源也时好时坏**。
**解决**：**全镜像私有化到 Harbor**——docker pull（走 docker daemon 加速器）→ tag → push Harbor → 集群改从 Harbor 拉。最终集群完全脱离外网依赖。
**经验**：国内环境做 K8s，**"镜像私有化"是终极解**。所有要用的镜像（业务/组件/调试 busybox）提前进 Harbor，别赌外网连通性。

### 2.3 VMware NAT 下 SSH 22 被代理拦截

**现象**：`ssh -T git@github.com` 连到 198.18.0.67（代理 fake-ip）超时。
**解决**：HTTPS push + PAT（凭据 store 保存）。
**经验**：VMware + 代理环境下 SSH 出站常被劫持，GitHub 用 HTTPS 更稳。

### 2.4 flannel VXLAN 单向不通（worker 重启后）

**现象**：worker 关机 7 天恢复后，master→worker 的 Pod 网络全不通（NodePort 访问监控 000），但 worker→master 正常。
**排查**：ping worker cni0（10.244.1.1）100% 丢包；查两端 flannel.1：**worker 的 flannel.1 只有 IPv6，丢了 10.244.1.0/32**；FDB MAC 一致（排除了 ARP 缓存问题）。
**根因**：worker 长时间离线后 flannel pod 多次重启，接口初始化不完整（IPv4 未配置）。
**解决**：删 worker 的 flannel pod 重建，IPv4 恢复，网络即通。
**经验**：**跨节点网络异常先看两端 flannel.1 的 IPv4 是否都在**，这是重启后最隐蔽的网络坑。

## 三、Kubernetes 资源编排

### 3.1 私有仓库的 imagePullSecrets 三连漏

**现象**：Deployment 从 Harbor 拉镜像报 `no basic auth credentials`。
**根因**：links 的 app/nginx 加了 imagePullSecrets，但 **StatefulSet（mysql/redis）、flannel DaemonSet、webhook Deployment** 都没加——每个新资源都忘了。
**解决**：chart 里给所有私有镜像资源统一加 `imagePullSecrets`。
**经验**：**私有仓库环境下，"给资源加 imagePullSecrets"必须成为 checklist**，Deployment/StatefulSet/DaemonSet/Job/CronJob 一个都不能漏。我当时漏了三次。

### 3.2 values.yaml 重复键（YAML 最隐蔽陷阱，踩了两次）

**现象①**：Jenkins helm 升级后 NodePort 变 ClusterIP。
**现象②**：Loki 主 Pod 不创建。
**根因**：values.yaml 里写了**两个相同顶层键**（如两个 `controller:`、两个 `loki:`）——YAML 后者整体覆盖前者，前面的资源配置全丢。
**解决**：合并成一个键块；用 `python yaml.safe_load` 校验顶层键唯一性。
**经验**：**values.yaml 反复追加配置时，检查有没有重复顶层键**。这是 helm 排障的高频原因。

### 3.3 helm 手动 upgrade 回退旧镜像

**现象**：Jenkins 流水线 helm upgrade（--set 新 tag）后，手动 helm upgrade 一次，业务回退到 v1 旧镜像（有 bug 的版本）直接 CrashLoop。
**根因**：`--set` 是临时覆盖，values.yaml 里 images 还是 v1。
**解决**：手动操作前先同步 values.yaml 的最新版本号。
**经验**：**helm 的 --set 与 values.yaml 要双向同步**，否则手滑一次就回退。这也是为什么推荐版本号由 CI 管理。

### 3.4 kubectl run 参数被移除（版本漂移）

**现象**：`kubectl run --image-pull-secrets` 报 unknown flag。
**根因**：kubectl 1.28 移除了该参数。
**解决**：改用 YAML 清单（也是更规范的做法）。
**经验**：kubectl 版本迭代会删参数，**写 YAML 比拼命令行参数更稳**。

### 3.5 helm 命令缺命名空间

**现象**：Jenkins 回滚 `helm rollback links` 报 `release: not found`。
**根因**：links release 在 default 命名空间（早期 install 没带 -n），资源却建在 links-ns——release 与资源命名空间不一致的历史遗留。
**解决**：helm 命令统一加 `-n default`；记录遗留问题。
**经验**：**helm install/upgrade/rollback 的 -n 必须一致**，否则 release 记录错位，且裸 uninstall 会连带删 PVC（有数据风险，我当时为避免丢数据选择保留现状）。

## 四、CI/CD（Jenkins on K8s）

### 4.1 docker.sock 权限 + docker CLI 版本

**现象①**：Jenkins agent 里 `docker build` 报 `permission denied`（socket）。
**根因**：inbound-agent 以 jenkins 用户运行，不在宿主 docker 组。
**解决**：agent `runAsUser: 0`（学习环境；生产用专用构建账号）。

**现象②**：`client version 1.43 is too old. Minimum supported API version is 1.44`。
**根因**：agent 内置 docker CLI 24（API 1.43），宿主 daemon 29（API 1.52）。
**解决**：agent 镜像的 docker CLI 升到 27。
**经验**：**挂宿主 docker.sock 必须对齐 CLI 与 daemon 版本**；宿主 docker 版本过新时这坑必踩。

### 4.2 Jenkins 镜像拉不动 → 全镜像私有化连锁反应

**现象**：Jenkins 主镜像 500MB 从 docker.io 拉取 ImagePullBackOff。
**根因**：大镜像走官方源必然失败（见 2.2）。
**解决**：docker pull（加速器）→ 推 Harbor → chart 换镜像源。连带把 agent 镜像、flannel、mysql、redis、busybox 全部私有化。
**经验**：这是"镜像私有化"决策的导火索，最终让整个集群受益。

### 4.3 Groovy 语法细节

**现象**：Jenkinsfile 第一行 `# 注释` 报 `expecting '!'`。
**根因**：Groovy 注释是 `//`，不是 `#`。
**解决**：改注释语法。
**经验**：Jenkinsfile = Groovy，别用 shell 习惯。

### 4.4 config.xml 回传 500

**现象**：Jenkins API 更新 job config 报 500。
**根因**：XML 里有中文特殊字符（→）导致解析失败（Unicode 0x88）。
**解决**：用纯 ASCII 重建 config。
**经验**：**操作 Jenkins API 时 XML 保持 ASCII**；中文放 description 里可能踩编码坑。

## 五、监控告警（阶段5）

### 5.1 node-exporter 9100 冲突

**现象**：master 上 node-exporter CrashLoop（`bind: address already in use`）。
**根因**：node-exporter 用 hostNetwork 监听宿主 9100，旧博客 docker 的 node_exporter 占着。
**解决**：停用旧博客监控组件（docker update --restart=no + stop），K8s 监控接管。
**经验**：**hostNetwork 组件的端口与宿主存量服务冲突**是常见问题，先排查再部署。

### 5.2 监控 NodePort 被 helm 覆盖

**现象**：helm upgrade 后 Prometheus/Grafana/Alertmanager 的 NodePort 全丢。
**根因**：kubectl patch 改的 NodePort 是临时状态，helm upgrade 按 values 重建 service。
**解决**：service type/nodePort 写进 values 固化。
**经验**：**helm 管理的资源别用 kubectl patch 改持久配置**，要么进 values，要么 patch 后不再 upgrade。

### 5.3 prometheus-operator 的 admission secret

**现象**：operator CrashLoop `open /cert/cert: no such file`。
**根因**：关闭 admissionWebhooks 后 chart 仍挂载 tls-secret，且我建的空 secret 没有 tls 内容。
**解决**：手动生成自签证书（cert/key）填充 secret。
**经验**：**operator 的 webhook 证书 secret 必须有 tls.crt/tls.key**；省资源关 webhook 前先确认 deployment 不挂载它。

### 5.4 Loki / promtail chart 7.x 配置漂移

**现象**：Loki 主 Pod 不建（只有缓存组件）；promtail 配置改了不生效；promtail 重复 job 报错。
**根因**：
- Loki 7.x 需显式 `deploymentMode: SingleBinary`；缓存组件开关在**顶层**（不在 loki 子键）
- promtail chart 顶层键是 `config`（不是 `promtail.config`）
- chart 默认已含 kubernetes-pods 采集，自定义 extraScrapeConfigs 撞名
**解决**：逐个修正 values 路径；删多余自定义。
**经验**：**大 chart 跨大版本时，values 结构可能整体重排**，先 `helm pull` 看官方 values 再写，别凭旧版记忆。

### 5.5 mysqld-exporter v0.17 忽略 DATA_SOURCE_NAME

**现象**：DSN 环境变量正确设置，仍报 `no user specified` 退出。
**根因**：v0.17 重写配置系统，**只认 .my.cnf 文件**，环境变量 DSN 被忽略。
**解决**：Secret 挂载 .my.cnf（[client] user/password/host/port），`--config.my-cnf=` 指向它。
**经验**：**exporter 类工具的小版本升级可能改配置方式**，看启动日志的报错段落（它明确说在解析哪个文件）。

### 5.6 告警规则不触发（for 时长认知）

**现象**：KubePodCrashLooping 一直 pending 不 firing。
**根因**：规则要求持续 900 秒（15 分钟），且 Prometheus 重启后重新计时。
**解决**：理解 for 语义；用 Watchdog（每 30s）快速验证链路，真实场景耐心等。
**经验**：**告警验证链路用 Watchdog 秒级验证，业务规则看 for 时长**。

## 六、环境与工具链

### 6.1 sudoers 引号地狱（最危险的一次）

**现象**：ssh 远程给 worker 配 sudo 免密，写入的 sudoers.d/zqq **语法错误**，worker 所有 sudo 失效——死锁。
**根因**：`ssh host "echo 'zqq ALL=(ALL) NOPASSWD:ALL' | sudo tee ..."` 的单引号在多层 shell 中被拆分，写入多行坏配置。且 echo 内容含空格被拆分。
**解决**：VMware 进 recovery mode（root shell）修复文件。
**经验**：**远程执行含引号/空格的复杂命令，一律用脚本文件 scp + sudo bash**，绝不在命令行拼引号。这是本项目最值得记住的教训。

### 6.2 sysctl handler 不触发

**现象**：Ansible 配置了 ip_forward=1，worker join 预检仍报错。
**根因**：notify handler 在某些主机未触发。
**解决**：手动 `sysctl --system` 兜底。
**经验**：**涉及内核参数的 playbook，handler 触发不可靠，改为任务内直接执行**。

### 6.3 worker 磁盘 10G 秒满

**现象**：监控 PVC 一挂，worker DiskPressure 疯狂驱逐。
**根因**：新 VM 默认 LVM 只分配了一半磁盘。
**解决**：VMware 扩盘 40G + `growpart` + `lvextend` + `resize2fs`。
**经验**：**新建 worker 先看磁盘空间**；LVM 场景扩盘三部曲记住。

### 6.4 needrestart 弹窗阻塞

**现象**：apt 装完包弹"Daemons using outdated libraries"。
**解决**：选 Ok 跳过；或 `sed` 改 needrestart.conf 自动应答。
**经验**：Ubuntu 无人值守安装必备配置。

### 6.5 浏览器 HTTPS-only 模式

**现象**：http 访问本地站报 SSL_ERROR_RX_RECORD_TOO_LONG。
**根因**：Firefox/Chrome 强制升级 HTTPS，访问的是明文端口。
**解决**：关 HTTPS-only 或配真 HTTPS（项目选了后者，顺势练了 ingress TLS）。
**经验**：本地 http 演示常被这坑绊倒，**配 HTTPS 是正解**（也练了证书体系）。

## 七、通用经验（可复用防呆清单）

1. **先看版本再查文档**：containerd 2.x / chart 7.x / kubectl 1.28，版本决定一切
2. **国内环境三件套**：静态 IP、阿里云源、镜像全私有化
3. **YAML 防呆**：重复顶层键、注释语法、引号嵌套——写文件比拼命令可靠
4. **helm 防呆**：values 与 --set 同步、-n 一致、NodePort 固化进 values
5. **私有仓库防呆**：imagePullSecrets 是 checklist 项
6. **验证防呆**：拉取验证用全新镜像；告警验证用 Watchdog；网络验证看两端接口
7. **排障套路**：kubectl describe（事件）→ logs（应用）→ journalctl（组件）→ 逐层缩小
8. **能写进代码/文件的，绝不手敲命令**（尤其远程、含引号、含密码的场景）
